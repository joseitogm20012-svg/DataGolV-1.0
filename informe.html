1 Introducción y Selección de la Entidad

Para el desarrollo de este primer proyecto práctico, se nos planteó el reto de diseñar e implementar desde cero una aplicación web estructurada bajo el patrón de arquitectura MVC (Modelo-Vista-Controlador), conectada a una base de datos No Relacional (NoSQL) y con un flujo CRUD completo.

En lugar de elegir las entidades convencionales como listas de tareas o catálogos simples de productos, optamos por un dominio más dinámico y retador: DataGol, un gestor inteligente de predicciones de partidos de fútbol. Nuestra entidad principal es Prediction (Pronóstico de Partido), la cual modela los equipos enfrentados, la competición, la fecha, las estimaciones porcentuales de victoria/empate, el marcador proyectado y el seguimiento del resultado final oficial.

2 Justificación del Entorno: Node.js y Express

  • Unificación tecnológica (JavaScript Full Stack): Seleccionamos Node.js porque nos permite trabajar con JavaScript tanto en el servidor como en los scripts del cliente y plantillas. Esto evita la fricción de cambiar de sintaxis entre el backend y frontend.
  • Arquitectura orientada a eventos no bloqueante: El motor V8 de Node.js gestiona las solicitudes HTTP y las operaciones de base de datos de manera asíncrona, garantizando alta velocidad de respuesta sin sobrecargar el servidor.
  • Express.js como Framework Web: Proporciona una capa ligera y flexible para administrar rutas HTTP (GET, POST, PUT, DELETE) y middlewares, facilitando una división limpia de carpetas sin imponer restricciones rígidas.

3 Justificación de la Base NoSQL: MongoDB Atlas & Mongoose

El enunciado del proyecto establece como requisito obligatorio el uso de una base de datos NoSQL. Nuestra decisión técnica se basó en los siguientes puntos:

  • Estructura flexible orientada a documentos (BSON/JSON): La información de un partido de fútbol encaja perfectamente en un documento JSON: métricas probabilísticas, factores clave de análisis y estados mutables (Pendiente → Acertada / Fallada).
  • Despliegue en la nube con MongoDB Atlas: Implementamos un clúster en la nube a través de MongoDB Atlas. Esto elimina la necesidad de configurar servicios locales en cada máquina, garantiza alta disponibilidad y permite que el proyecto sea probado inmediatamente por cualquier evaluador al clonar el repositorio.
  • Validación estricta con Mongoose ODM: Para asegurar la consistencia requerida, implementamos un esquema con validaciones nativas:
    • Obligatoriedad y longitud mínima en nombres de equipos.
    • Validación personalizada para impedir que el equipo local sea igual al visitante.
    • Restricciones numéricas que impiden registrar goles o probabilidades negativas.

4 Justificación del Motor de Plantillas: EJS

Elegimos EJS (Embedded JavaScript) por encima de otras opciones como Pug o Handlebars debido a:

  • Sintaxis natural basada en HTML estándar: EJS conserva la estructura tradicional de etiquetas HTML, insertando código de servidor únicamente donde se necesita mediante etiquetas <%= %>. Esto evita los errores comunes de indentación propios de otros motores.
  • Componentización modular (Partials): Dividimos la interfaz en fragmentos reutilizables (partials/header.ejs, navbar.ejs, footer.ejs, alerts.ejs), aplicando el principio DRY (Don't Repeat Yourself) y facilitando el mantenimiento global del diseño.

5 Estructura y Separación de Capas (MVC)

El proyecto respeta de manera estricta la separación de responsabilidades solicitada por la cátedra:

PROYECTOPROGRAMACION III/ ├── config/ # Conexión a MongoDB Atlas (db.js) ├── models/ # Esquema y validaciones de datos (Prediction.js) ├── controllers/ # Lógica de negocio y control del CRUD (predictionController.js) ├── routes/ # Enrutamiento semántico REST (predictionRoutes.js) ├── utils/ # Algoritmo de cálculo de probabilidades (predictionEngine.js) ├── views/ # Vistas dinámicas en EJS (index, create, edit, details, error) ├── public/ # Recursos estáticos (CSS personalizado, Bootstrap 5) ├── .env.example # Plantilla de variables de entorno └── app.js # Inicialización del servidor Express
  • Model (models/Prediction.js): Define la estructura del documento en MongoDB y ejecuta las reglas de integridad de datos.
  • Controller (controllers/predictionController.js): Contiene la lógica del negocio: consulta a la base de datos, calcula los KPIs del dashboard, procesa las solicitudes del usuario y decide qué vista renderizar.
  • Routes (routes/predictionRoutes.js): Mapea las URLs con los métodos del controlador. Utiliza el middleware method-override para soportar verbos PUT y DELETE directamente desde formularios web.
  • View (views/): Despliega la información procesada sin interactuar jamás directamente con la base de datos.

6 Lógica de Negocio: Motor Estadístico de Predicción

Para enriquecer la aplicación más allá de un CRUD básico, implementamos en utils/predictionEngine.js un algoritmo de simulación deportiva:

  • Analiza los índices de poder ofensivo y defensivo de los equipos enfrentados.
  • Aplica un factor ponderado por ventaja de localía (+6% al rendimiento del anfitrión).
  • Calcula probabilidades normalizadas de victoria local, empate y visitante (sumando exactamente el 100%).
  • Ofrece un endpoint /api/simulate que permite al usuario ver la simulación en tiempo real mediante peticiones asíncronas (AJAX) antes de almacenar el pronóstico.
  • Evalúa de forma automática si un pronóstico fue Acertado o Fallado al momento de cargar el marcador oficial en la vista de edición.
